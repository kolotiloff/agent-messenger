# Broker: what is built (T-015, first part)

Status on 2026-11-13 (0.66 released, 0.67 in preparation): the background client can host a broker, a computer can join a broker by invitation or short code, every computer sees the others with their agents and tasks, and a coordinator can give, answer, continue, note and cancel tasks on another computer (T-037, see [TASK_MODEL.md](TASK_MODEL.md#tasks-between-computers-t-037)). The owner can update another computer from the window, and a coordinator can read another computer's log when that computer allows it. The placement principles are in [DEPLOYMENT.md](DEPLOYMENT.md).

## What works

- **Hosting** (D-033). The background client runs the broker inside its own process when the owner turns it on in the window. Off by default. Access is "only this computer" (`127.0.0.1`) by default; "local network" listens on all interfaces, lists the computer's private IPv4 addresses for invitations, and drops any peer that is not on this computer or a private network (a public IPv6 address, for example) before TLS. Port 47100 by default, 1024–65535 allowed. A busy port is refused with a clear message, and the previous settings and the running server are kept. The setting is remembered and the broker starts again with the client.
- **Limits.** At most 64 open connections (the broker shares the client's process, so a flood must not use up its files), and at most 16 from one other computer (one IPv4 address or one IPv6 /64), so one host of the network cannot take every slot; this computer itself is limited only by the total. No keep-alive, short timeouts. After 20 wrong registration attempts in a minute from one source the broker answers "too many attempts" to that source without touching its database; other computers can still join. A wrong secret never takes the database write lock. Device names are one printable line, without control or direction-override characters.
- **No redirects.** The device's clients never follow a redirect: a `3xx` answer is an error, so the device key cannot be carried to another address or to plain HTTP.
- **Short codes on the local network** (T-052). The discovery listener (UDP, port 47100) answers only this computer and private networks, like the broker itself. The joining computer keeps every answer per (broker ID, address), at most two per address and eight in all, because any computer of the network can answer with the real host's broker ID. It tries them in turn: a server that cannot prove the code in the exchange, or has no open invitation, does not end the search, and each server (told apart by its certificate) is asked once, so the real host answering on several addresses loses only one of its three tries to a wrong code.
- **Identity and TLS.** On first start the broker creates a stable `broker_id` (`brk-` + 16 hex) and a self-signed ECDSA P-256 certificate. TLS 1.3 only. Clients trust exactly that certificate by its SHA-256 fingerprint; host names are not used for trust.
- **Invitations.** The owner picks one of the broker's addresses and gets a one-time code `am1:…` (base64url JSON with address, `broker_id`, fingerprint and a 256-bit secret). Valid for 15 minutes, used once, stored as a hash. The window hides the code once a new device has joined.
- **Joining** (D-034). The other computer pastes the code and a device name. It first connects with the pinned fingerprint, checks `broker_id` and protocol version (`GET /v1/hello`), and only then sends the secret (`POST /v1/register`). It receives a device ID and a 256-bit device key; the broker stores only a hash of the key. A computer belongs to one broker: joining another one requires "Отключить" first, so nothing is ever sent to a new broker silently. A computer that hosts a broker cannot join another one, and one that joined cannot start its own (D-111). «Отключить» first asks the broker to revoke the device (`POST /v1/leave` with the device key; an older broker answers 404 and the device stays until the host revokes it).
- **Checking.** "Проверить связь" repeats the identity check and calls `GET /v1/ping` with the device key. A revoked or unknown key is reported as such; an unreachable server or a different certificate are reported separately.
- **Devices.** The host lists devices with their last contact and can revoke one. Revocation takes effect on the next request. Revoked devices are counted, not listed.
- **Computers and agents** (D-039). Every 15 s the client reports its agents to the broker (`POST /v1/presence` with the device key; the hosting computer writes its own report directly): each agent program with its running and waiting-for-owner task counts, and the coordinator program. Since 0.67 it also reports how many messages it has not handed to the broker yet and the age of the oldest (`outbox`, T-150), so the others can tell late replies from lost ones, and which other computers' tasks it runs a worker for now, with the age of that worker's last output (`workers`, T-149). The answer is the list of computers: the hosting computer (under `host`) and every device that is not revoked, each with its last report and how many seconds ago it came by the broker's clock (clocks of computers may differ). The window's sidebar shows the other computers like this one; a computer that has not reported for 45 s shows «Был на связи …». A device's report carries the name set in its window, and the broker renames the device to it, so a rename reaches every computer within one report (D-061). A name that the hosting computer («Сервер» if it set none) or another active device already has, compared without case and surrounding spaces, is not taken: the report is kept under the old name, and the device keeps the name its roster entry shows; a report with an unknown field, a bad agent name, a negative count or duplicates is refused. A successful report also counts as a connection check; a failed one is shown and the next round, 15 s later, tries again. A computer that joined its own server does not list itself. An older device with the name of a newer device that reported later is left out of the list, not revoked: it is the same computer that joined again (T-127, D-111). A member also leaves out its own earlier devices and any device under its own name.
- **Mailbox** (T-037, D-041). `POST /v1/send {to, op_id, body}` stores a message for another computer of the broker (`host` or a device ID); `POST /v1/inbox {after}` deletes the caller's messages up to `after`, which it has applied, and returns the next ones in order (at most 16). The broker never reads a body (a JSON object up to 256 KB). The same `(sender, op_id)` is stored once while it waits; an unknown or revoked recipient is refused (404 `recipient`), a recipient with 500 unread messages too (429), and so is a sender that already has 100 unread messages for that recipient, so one computer cannot fill another's mailbox for everybody. Revoking a device drops the mail to and from it. The hosting computer uses the same mailbox directly, under `host`. An older broker without the mailbox answers 404 without `recipient`; the window then says the server must be updated.
- **Sending order** (D-119). The client sends its outbox in batches of 50, oldest first, each recipient's messages in order. A recipient whose mailbox is full is left out of the next batch, so its waiting messages never hold back messages to other computers. They stay queued and are tried again each round.
- **Parked replies** (D-121). When the broker refuses a message because its recipient is not in the network, a reply about another computer's task (its event, acceptance, refusals, output) is parked, not deleted. It stays in the outbox, is not sent while parked, and goes again when that computer is listed under the same ID or moves to a new ID (D-115). The receiver applies it once by its operation ID. Other messages keep their handling (see [TASK_MODEL.md](TASK_MODEL.md#tasks-between-computers-t-037)).
- **Messages that are not tasks.** The mailbox also carries `log_request` / `log` (D-083) and `update_request` / `update` (T-078). A computer answers a log request only when its owner turned on «Отдавать журнал по сети» on the «Сервер» tab (off by default); session IDs, codes and keys are removed from the lines it sends. An update request comes from the «Обновить до …» icon on another computer's card; that computer installs the newest signed update only while it runs no tasks (a Mac refuses and updates in its own app), and answers at once and again with the final result. Nothing is retried on its own.
- **Shared task lists** (T-047). `POST /v1/tasks` sends this computer's recent tasks (at most 50) and returns the other computers' lists, read-only. The broker keeps only the latest list of each computer.
- **Disconnect** («Отключить») first asks the broker to revoke this device (`POST /v1/leave`), then forgets the connection on this computer. When the broker cannot be reached or is too old, the device stays listed there until the host revokes it; this computer still remembers it and never lists it as another computer (D-111).

## Computers in different places

The broker has no internet mode. Computers in different homes still work together when they share a VPN that gives them private addresses (10.x, 172.16–31.x, 192.168.x, or IPv6 fc00::/7): to the broker they are one private network, so "local network" accepts them (D-040).

- The VPN keeps outsiders away from the broker. Inside the VPN a computer still needs an invitation or the short code, and all traffic is TLS with the broker's pinned fingerprint, so the VPN server only carries encrypted data.
- A VPN that hands out 100.64.0.0/10 addresses is refused: Go does not count that range as private. Change the VPN's address range, or ask for this to be allowed as a separate decision.
- Finding the server automatically uses local broadcast and usually does not cross a VPN; join by the address in the invitation.
- The computer that hosts the broker must stay on and awake; while it is off, the others cannot exchange tasks.
- Give other people their own broker and their own VPN rather than a place in yours.

## Files

In the client's data directory:

| Path | What |
|---|---|
| `broker/settings.json` | hosted broker: on/off, scope, port |
| `broker/broker.sqlite` | `broker_id`, devices (key hashes), invitations (secret hashes), the latest presence of each computer, messages waiting for their recipient |
| `broker/tls-cert.pem`, `broker/tls-key.pem` | the broker's certificate and private key (0600) |
| `broker/serve.lock` | one running broker per data directory |
| `server-connection.json` | this computer's membership, including the device key (0600; Q-013) |

Files are written to a fresh temporary file, flushed to disk and renamed. A damaged settings or connection file never stops the client: the window shows the problem and the file is left as it is. A damaged connection file blocks joining a broker until the owner presses «Отключить», which deletes it.

## Interfaces

- Control command `server` with actions `status`, `enable`, `disable`, `invite`, `revoke`, `connect`, `check`, `disconnect`, `rename`, `accept` (`{"on": true|false}`: run tasks of other computers), `net_full_access`, `log_share`, `update` (ask another computer to update). Accepting is on by default (D-056, replacing Q-014's cautious default); the owner turns it off with «Принимать задачи других компьютеров». Sharing the log is off by default; the owner turns it on with «Отдавать журнал по сети» (D-083). Tasks from the network take the agent's «Любые команды» unless the owner turns off «И для задач с других компьютеров» on «Агенты»; it is on by default (D-109, replacing D-097's default). The status never contains the device key; it carries `accept`, `log_share` and the last task-exchange problem (`network_error`).
- Window API: `GET /api/server`, `POST /api/server-action` (same rules as other window actions: token, Origin, JSON, bounded fields).
- Timeouts: each broker request 15 s, a window server action 18 s in the client, 22 s at the window route, 28 s in the page. If the page gets no answer it says the result is unknown and asks to check the state before repeating.
- `messenger status` shows `broker=not_configured|hosting|connected|hosting+connected`.

## Not built yet

- A standalone broker for a VPS and the VPS setup wizard (D-035). Optional: one local network needs no VPS (D-040).
- Keeping the device key in the OS secure storage (Q-013).
- A reachability check from another computer. "Работает" means the broker listens; it does not prove that another computer can reach it (firewall, VPN, router).

## Verified

On Linux with tests (`internal/broker`, `internal/supervisor/server_test.go`, `internal/localui`) and in headless Chromium against a real client: enable, invite, join (the client joins its own broker, as a second computer would), check, revoke (two clicks) and the check after it, a wrong code, a wrong port, disable, "local network" on a machine without a private address. An audit of the code found and fixed: no connection limit, LAN scope reachable from public addresses, a restart racing its own lock, shutdown closing the database under running requests, settings not saved while the server ran, parallel joins leaving a stray device, files not flushed, device names with control characters, misaligned timeouts, and window issues (the access picker not showing the saved scope, a used invitation still shown, lost keyboard focus, status texts cleared by an older timer, a slow poll overwriting a newer state, revoke in one click). Presence (D-039): broker tests for the roster in both directions, refused reports, revoke, an unreachable broker; headless Chromium with a helper that joins as a second computer and reports two agents: its card with Claude (coordinator) and Codex, «Был на связи» after it stops, revoke from the right-click menu. Mailbox (T-037): broker tests for order, acknowledgement, a repeated operation, refusals, a full mailbox, revoke; a supervisor test where two stores exchange a task through a real broker over TLS; and two separate clients on one Linux machine (the second with its own home directory), joined through the window API: a coordinator on one started a task for the other, it was accepted with its folder, cancelled from the first, and a second task was refused while the other computer did not accept tasks. Not verified: two real computers, the Mac app, a local network.

Security hardening (2026-11-09), broker tests only (`internal/broker/security_test.go`): clients do not follow redirects, per-source connection and registration limits, refused renames to taken names, the per-sender mailbox share, discovery answering only local sources, and pairing that tries every candidate without costing the real host extra tries. Not verified on two real computers.
