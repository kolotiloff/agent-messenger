## T-154

Local cards reserve an 88 px action column and 56 px rows. Row actions stay 28 px high. Titles clip with a tooltip, and informational rows use the available text width. Version, login and tested-version marks remain visible during a new check; actions are disabled while it runs. A failed diagnostic replaces the previous login confirmation with an unknown result. Duplicate checks for the same provider are suppressed.

An unchanged provider card keeps its DOM nodes, including focus, when another card or the window updates. The comparison includes CLI/profile paths so retained callbacks cannot use an older path. After opening installation, returning to the window searches for the program again; a newly discovered path receives the normal non-model diagnostic. Installation itself is still the existing official-page action (T-153 remains separate).

Browser verification used the actual embedded HTML/CSS/JS in headless Chrome on macOS, with all HTTP requests answered by fictional fixtures. No Messenger client, working sessions, registry or model was used. Checked:

- Same row positions and text widths before/during/after a check, authenticated-to-signed-out transition, a failed check, installation notice and newly discovered CLI.
- Previous version, login and newer-version warning retained during the pending request; unknown login after failure.
- Unchanged card identity and keyboard focus across a window refresh; another provider's card retained during a check.
- Installation return triggers discovery and diagnostic; no duplicate check on focus during an in-flight check.
- Light/dark themes at 1100 and 600 px: tasks, agents, server, agent-settings dialog and theme menu screenshots. All measured local rows were 56 px; row action buttons were 28 px. No browser script errors.

Native AppKit/WebView2/WebKitGTK windows and actual installation/login were not exercised.

## T-161

Read-only inspection of the owner's reported Codex coordinator chat confirmed the distinction: worker events reached Messenger and the shell watch exited, but the idle chat did not resume. The next owner message caused the coordinator to read the saved questions successfully. No working chat was used as a test session or sent a message during this investigation; no chat/task identifiers or conversation transcript are included here.

The old instructions unconditionally told every client to end its turn and promised the background command would wake it. The correction (D-124) chooses active wait for Codex and unknown clients, and background watch only for the known `claude-code` client when a command is available. Active mode asks for 30-second waits and continued monitoring within the active turn, with owner messages handled between calls. The mode appears in initialize and in tasks/wait/start/answer/continue results. No new mechanism to resume an already-idle Codex chat was added.

Protocol tests cover Codex, Codex Desktop, Cursor, Cursor Agent, Claude Code, unknown and unnamed clients: initialization instructions, task results, wait timeouts and watch availability. Existing event wake, cancellation, cursor replay and supersession tests remain applicable. A separate real Codex acceptance run is still required to establish that the model follows the corrected guidance and remains responsive to owner messages.

The official [MCP configuration documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) confirms the default 60-second tool timeout; the existing generated Codex configuration allows 180 seconds, so the observed completed watch is not evidence of an MCP tool timeout. The documented [MCP Events integration](https://developers.openai.com/plugins/build/mcp-events) targets Work cloud chats and dots over HTTP/webhooks; it is not the local stdio connection implemented here.

## T-162

Cursor is offered on the project and welcome pages. The connection writes only the project's `.cursor/mcp.json`, not the global configuration. It preserves other servers, large numeric values and options inside an owned entry when updating the program path. Foreign/disabled entries, malformed or duplicate JSON, oversized files and symlinks are refused or left unchanged. File permissions are preserved. The saved environment explicitly forwards the worker guard, using the same interpolation mechanism as the existing Cursor worker tools.

Adapter tests cover create/read/idempotence, stale entry repair with extra options, foreign and disabled entries, invalid/duplicate/large JSON, and file/directory symlinks. Supervisor tests cover missing Cursor, connection, the window read model, preservation of a foreign entry and absence of a global config write. The HTTP route accepts Cursor and still rejects unknown agents. Translation coverage passes.

A fake Cursor MCP client initialized, started a fixture worker, blocked in `wait`, received its question, answered it and received its report at a later cursor. The results carry active-wait instructions and do not promise background wake-up. No real Cursor process/model was used for this test.

Browser fixtures exercised the Cursor connection action, the generated manual JSON (including the guard), and connected/foreign/disabled/unreadable/unregistered states. Project-page screenshots were taken in both themes at 1100/600 px, with no script errors. Real Cursor approval, tool discovery and model-driven waiting remain for the owner's separate acceptance run.

Configuration and approval behavior follow the official [Cursor MCP guide](https://cursor.com/docs/mcp) and [Cursor CLI MCP guide](https://cursor.com/docs/cli/mcp). Saving the file is not proof that Cursor has approved or connected the server, so the window labels it as saved and asks for normal approval. No undocumented timeout setting or automatic approval of other tools is added.
