# Постоянный журнал исходящих: Mac, 6 ноября 2026

Изменение поверх `772398e` (PR #11). macOS arm64, Go 1.22.2. Полный набор `go test -race -count=1 -ldflags=-linkmode=external ./...` прошёл. Внешний линкер выдаёт прежние предупреждения LC_DYSYMTAB, тесты завершаются успешно. Linux/amd64 и Windows/amd64 собраны с `CGO_ENABLED=0`; runtime на них в этой проверке не запускался.

## Что проверено

- Конверт хранится в `ui_outbox` SQLite клиента, с зафиксированными ID, текстом, псевдонимом и ключом сессии. `ui-prepare` не создаёт requests или attempts.
- Закрытие и повторное открытие SQLite сохраняет подготовленный конверт. После `ui-submit` повторное открытие сохраняет queued. Двенадцать конкурентных повторов submit не создают новые requests.
- Подменённые адрес и текст с тем же ID отвергаются. Сбой обновления исходящих внутри транзакции откатывает также вставку задания. Если queued-запись есть, а задание удалено, повтор, чтение с заявлением об успехе и ACK запрещены. Автоматического ремонта с повтором работы нет.
- Подтверждение просмотра идемпотентно, не удаляет задание и не скрывает подготовленное письмо. Лимит 100 неподтверждённых исходящих действует; подтверждение queued освобождает место. Совпадающее старое UI-письмо принимается в журнал без второго задания. Проверен `PRAGMA synchronous = 2` (FULL).
- HTTP-тест имитирует потерю ACK после ui-prepare: дальнейшего submit нет; три чтения outbox не создают заданий. Другой тест теряет ответ после submit и проверяет повторы. Защита Host/Origin/ключа и ограниченного JSON сохранена, новые чтение и ACK не доступны без нужного метода/ключа.

## Опыт с настоящим окном на Mac

Изолированные HOME, профиль, SQLite и рабочая папка. Зарегистрирована синтетическая привязка `codex-check` с `/usr/bin/false`; настоящий Codex не вызывался. Клиент без разрешения моделей, очередь на паузе.

1. Через настоящий control API сохранены два конверта: один prepared, второй queued без ACK окна. Окно показало разные состояния и разные действия.
2. Вкладка полностью закрыта. Только тестовый клиент принудительно завершён SIGKILL, UI-процесс остановлен. Это имитация сбоя приложения, не отключение питания и не перезагрузка Mac.
3. Тот же каталог открыт новым клиентом и новым UI-процессом. Созданы новая вкладка, новый порт и ключ; старая sessionStorage не использовалась. Оба конверта восстановились.
4. Подтверждение queued убрало его из списка восстановления, сохранив историю. «Восстановить отправку» для prepared перенесло исходные ID/адрес/текст в редактор. На этом этапе в SQLite по-прежнему одно задание и ноль попыток: восстановление ничего не отправило.
5. Явное двойное нажатие повторной доставки создало второе задание ровно один раз. Затем обычная отправка нового письма создала третье. После обновления страницы список восстановления пуст, все три письма видны в истории. SQLite: три requests, три acknowledged outbox, ноль attempts.
6. Тестовые процессы остановлены. Рабочие чаты, профили и защитные резервы не использованы. Режим бодрствования Mac, отдельно запрошенный пользователем, оставлен действовать до своего срока.

## Границы

Сохранение гарантируется после первой успешной записи конверта клиентом. Неотправленный текст в поле и конверт, который не достиг недоступного клиента, ещё не являются постоянными черновиками. SessionStorage остаётся дополнительной защитой текущей вкладки. Восстановление не чинит удалённую/повреждённую базу и не повторяет модельную работу. Настоящие модели в этом этапе не запускались.
