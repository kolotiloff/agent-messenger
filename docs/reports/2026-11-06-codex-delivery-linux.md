# Codex message delivery: Linux checks

2026-11-06, cloud session (Linux x86-64), Go 1.24.7. No model was called. The turn protocol was taken from the schema generated by Codex CLI 0.155.1 (`TurnStartParams`/`Response`, `TurnCompletedNotification`, `DynamicToolCallParams`/`Response`, server request list). It was exercised against a fake app-server, not against a real model. This is not a Mac acceptance run.

## Automated checks

`bash scripts/check.sh` passed: gofmt, `go mod verify`, `go vet` and all race tests. `scripts/check-builds.sh` passed for darwin/arm64, darwin/amd64, linux/amd64 and windows/amd64 (compile only). The opt-in setup check against real Codex 0.155.1 (`MESSENGER_CODEX_PROBE`) still passes; it does not start a turn.

New and changed tests:

- `internal/adapters/codex_rpc_test.go` (`RunTurn`):
  - The happy path with a tool call that arrives before the `turn/start` response passes.
  - These outcomes are rejected:
    - refused `turn/start`;
    - completed without a reply;
    - `failed` status;
    - repeated server request ID;
    - unexpected response mid-turn;
    - foreign turn;
    - EOF;
    - missing or mismatched turn ID;
    - more than 256 early frames;
    - stale receipt;
    - an extra model-chosen field.
  - In every rejected case `turn/start` was written exactly once.
  - A failing `Prepare` writes nothing.
  - An approval request gets an error response and the turn still completes.
- `internal/core/codex_setup_test.go`:
  - The owned session is registered without a CLI path.
  - Generic claims and launch configuration refuse it.
  - The state order holds: claim, send intent, bind, read, reply, complete. Each step refuses to run out of order or twice.
  - A failure leaves the owner uncertain and the session locked, also after a restart.
- `internal/supervisor/codex_setup_test.go`, full client with the fake app-server:
  - Two messages are served by one process with replies `ACK:one` and `ACK:two`, routed to the sender. There are 2 verifications with `provider_ok=1` and 2 `turn/start` calls. This holds in normal, early-call and approval modes.
  - Pause holds the message; resume delivers it.
  - Each of these failures leaves the message and owner uncertain:
    - `failed` status;
    - no reply;
    - foreign turn;
    - duplicate request ID;
    - exit during the turn;
    - failure of the second turn.
  - After a failure the next message stays queued, the `turn/start` count is unchanged, the reservation is kept and `resolve retry` is refused.
  - With `--only-session`, the generic loop never launched the Codex session; only the owner served it.
