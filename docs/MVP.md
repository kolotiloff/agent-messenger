# Поэтапный MVP v0.2: сначала приложение на Mac

Обновлено 5 ноября 2026 года по запросу пользователя. Интерфейс, статусы, переписка и установка из GitHub входят в целевой MVP. На время доступности только Mac проверки и первая пользовательская версия выполняются локально. Mac↔Windows остаётся обязательной следующей приёмкой сети.

## Где мы сейчас

На Mac проверены базовые resume Claude/Codex/Cursor, реальные пары Codex–Cursor и Codex–Claude через прежний MCP. В новом локальном стенде прошли 13 синтетических тестов привязки ответов, очереди и единственного владельца сессии. Готового приложения и установщика нет. Актуальные результаты — в [VALIDATION.md](VALIDATION.md).

## Этапы

| Этап | Результат и условие перехода |
|---|---|
| 1. CLI под контролем клиента — текущий | Новый reply-контекст и резервирование работают с реальным CLI. Два последовательных задания продолжают точный ID; конкурентный запуск блокируется; неверный ID/нет результата не считаются успехом. Сначала Claude, затем Codex/Cursor. |
| 2. Восстановление и локальное ядро | Явные состояния, журнал, очередь, пауза и остановка. При сбое нет автоматического повтора; восстановление проверяет идентичность/дерево процессов и зафиксированный ответ. UI получает документированный локальный API событий/команд. |
| 3. Первое окно на Mac | Карточки агентов, обнаружение CLI и входа, понятные действия установки/авторизации, список проблем, переписка и форма отправки. Данные реальные, а не демонстрационные статусы. |
| 4. Локальный выпуск для Mac | Устанавливаемая сборка в GitHub Releases, инструкция для человека и агента, проверка чистой установки/обновления/удаления. Очереди и секреты не входят в сборку. |
| 5. VPS и Mac↔Windows | Авторизация устройств, адресация, устойчивая сетевая доставка, повтор после offline, отзыв токена, восстановление брокера. Та же переписка и статусы видны в приложении. |
| 6. Надёжность сетевого MVP | Два последовательных межмашинных обмена с resume, проверки сбоев, час ожидания без запусков модели, отсутствие дублей и безопасная ручная передача сессии. |
| 7. Четыре компьютера и координатор | Windows x2 и Linux, установочные пакеты, автозапуск/сон, смена роли координатора с журналом и сохранением активных задач. |
| 8. Необязательные дополнения | Telegram-зеркало и дополнительные адаптеры агентов; после основной приёмки. |

Этапы могут частично пересекаться: макет окна можно делать после определения состояний, не дожидаясь готовности VPS. Рабочие сессии проекта не подключаются автоматически вместо тестовых.

## Первый локальный пользовательский сценарий

Установить приложение → увидеть три карточки агентов → установить недостающий CLI/войти штатным способом → создать управляемую тестовую сессию → выбрать адресата и отправить сообщение → увидеть очередь, обработку и связанный ответ → отправить второе письмо в ту же сессию.

Открытый интерактивный разговор получает статус ручного владения. Автоматический resume ждёт явной передачи управления клиенту.

## Приёмка

Локальный выпуск требует этапов 1–4 и проверок [интерфейса](APP.md). Сетевой Mac↔Windows MVP требует также 5–6. Поддержка всех четырёх компьютеров и смена координатора подтверждаются отдельно на этапе 7.

Готовность означает: один владелец сессии; сообщения и ответы сохранены; дубликаты не вызывают модель; потеря сети не теряет письмо; неопределённый результат требует разбора; ожидание и UI не вызывают модель; человеку понятны ошибки и необходимые действия.

Unity остаётся в Plastic SCM. Вложения, перенос внутренней истории между провайдерами, управление Unity и автоматическое ведение roadmap не входят в MVP. Простой интерфейс статусов/переписки теперь входит.

## Восстановление из uncertain — требование этапа 2

1. Остановить выдачу новых заданий этой привязке и отозвать старый контекст записи результатов.
2. Сопоставить конкретное исполнение с профилем, ID разговора, рабочей папкой и идентичностью процессов, включая потомков. Номер PID или истёкший таймер недостаточны.
3. Если нельзя доказать прекращение исполнения, оставить блокировку и показать причину.
4. Сверить сохранённый ответ и события CLI. Отделить сохранённый ответ от подтверждённого завершения процесса; неполный журнал не считается успехом.
5. Зафиксировать решение в журнале: принять проверенный результат, завершить с ошибкой без повтора либо явно создать новую попытку после разбора. Старый результат не затирается; побочные действия не предполагаются обратимыми.
6. Только после проверки остановки и решения по результату разрешать следующие задания. Автоматическое продолжение на другой машине не заменяет эту процедуру.

Снятие блокировки и повтор пока не реализованы в тестовом ядре; текущий стенд намеренно блокирует сомнительные исполнения.
